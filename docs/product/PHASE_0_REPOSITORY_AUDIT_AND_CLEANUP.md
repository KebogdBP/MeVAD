# Phase 0 — Repository Audit and Cleanup

**Проект:** MegaDownloader Video & Audio  
**Статус:** выполняется  
**Тип документа:** рабочий план и чек-лист  
**Основание:** `MEGADOWNLOADER_PROJECT_VISION.md`  
**Следующая фаза:** Phase 1 — Downloader Core Refactoring

## 1. Цель

Подготовить чистую, безопасную и воспроизводимую основу для дальнейшего
выделения `downloader-core`, не меняя поведение существующего CLI.

Phase 0 не является архитектурным рефакторингом. На этом этапе нужно:

- установить фактическое состояние legacy-приложения;
- сохранить и зафиксировать работающие пользовательские сценарии;
- убрать из Git секреты, результаты обработки и платформенные бинарники;
- сделать установку, запуск и проверки воспроизводимыми;
- создать минимальные защитные тесты перед переносом логики в core.

## 2. Текущее подтверждённое состояние

На момент создания документа в рабочей папке находятся:

```text
MeVAD/
├── MEGADOWNLOADER_PROJECT_VISION.md
└── docs/
    └── product/
        └── PHASE_0_REPOSITORY_AUDIT_AND_CLEANUP.md
```

Канонический remote:

```text
https://github.com/KebogdBP/MeVAD
```

На 25 июля 2026 года remote является пустым: ветка `HEAD` и коммиты
отсутствуют. В локальной папке не обнаружены:

- Git-репозиторий и история коммитов;
- Python-код существующего CLI;
- файлы зависимостей;
- тесты;
- локальные бинарники FFmpeg;
- конфигурация CI;
- README;
- Docker-конфигурация.

Следовательно, этот репозиторий начинается как greenfield-проект. Утверждения о
поведении прежнего CLI относятся к другому репозиторию и пока не подтверждены
в MeVAD. До отдельного решения об импорте legacy-кода нельзя фиксировать его
зависимости или подтверждать работоспособность его сценариев.

## 3. Границы фазы

### Входит в Phase 0

- получение полного legacy-репозитория вместе с историей Git;
- инвентаризация кода, данных, бинарников и зависимостей;
- ручная проверка существующих CLI-сценариев;
- фиксация текущего поведения smoke-тестами;
- упаковка и инструменты качества Python;
- очистка Git и документации;
- базовый CI;
- план переноса файлов для Phase 1.

### Не входит в Phase 0

- создание Next.js, FastAPI, worker, PostgreSQL или Redis;
- изменение UX терминального меню;
- разделение CLI и доменной логики;
- переписывание команд `yt-dlp` и FFmpeg;
- добавление новых форматов или функций;
- Docker Compose для полной SaaS-архитектуры;
- оптимизация производительности.

Исключение допустимо только для минимальных исправлений, без которых
невозможно установить или запустить текущий CLI. Такие изменения должны быть
отдельными маленькими коммитами.

## 4. Принципы выполнения

1. Сначала зафиксировать поведение, затем менять структуру.
2. Не удалять неизвестные файлы до классификации и резервной точки в Git.
3. Не коммитить пользовательские медиа, cookies, токены и результаты загрузки.
4. Не вызывать внешние команды через shell-строки.
5. Не смешивать cleanup и Phase 1 refactoring в одном pull request.
6. Каждый шаг должен оставлять CLI запускаемым либо явно помечаться как
   подготовительный.

## 5. Порядок работ

### Step 0. Подключить канонический репозиторий

- [x] Определить канонический remote и владельца репозитория.
- [x] Проверить remote, ветки и теги.
- [x] Подтвердить отсутствие истории и legacy-кода в новом remote.
- [x] Зафиксировать greenfield-статус в отчёте аудита.
- [ ] Создать рабочую ветку `chore/phase-0-repository-cleanup`.
- [ ] Не копировать `.git` вручную между папками.

**Контрольная точка:** `git status` чистый, remote доступен, исходная точка
проекта документирована.

### Step 1. Снять инвентаризацию без изменений

Создать `docs/audits/legacy-repository-audit.md` и записать:

- [ ] дерево файлов с назначением основных модулей;
- [ ] точки входа CLI;
- [ ] версию Python и поддерживаемые ОС;
- [ ] прямые и транзитивные зависимости;
- [ ] способы поиска `yt-dlp`, FFmpeg и FFprobe;
- [ ] места чтения и записи файлов;
- [ ] использование `input()`, `print()`, `subprocess` и shell-команд;
- [ ] сетевые вызовы, cookies, proxy и переменные окружения;
- [ ] временные каталоги и правила именования результатов;
- [ ] дубликаты, архивы, generated-файлы и крупные файлы;
- [ ] потенциальные секреты без копирования их значений в отчёт;
- [ ] существующие тесты, линтеры, CI и документацию.

Полезные категории для каждого файла:

| Категория | Решение |
|---|---|
| Исходный код | оставить и описать |
| Конфигурация | проверить и нормализовать |
| Тесты | запустить и сохранить |
| Документация | обновить |
| Бинарник инструмента | заменить системной/контейнерной зависимостью |
| Результат загрузки | исключить из Git |
| Секрет или cookies | немедленно исключить и ротировать |
| Дубликат/backup | удалить после подтверждения |
| Неизвестно | не удалять до выяснения |

**Контрольная точка:** для каждого отслеживаемого файла известно назначение и
план дальнейшего действия.

### Step 2. Зафиксировать baseline поведения

Проверить в чистом временном окружении:

- [ ] запуск справки и выход из CLI;
- [ ] скачивание одиночного видео;
- [ ] извлечение MP3;
- [ ] выбор качества;
- [ ] скачивание плейлиста;
- [ ] отображение прогресса;
- [ ] обрезку по времени;
- [ ] понятную ошибку для неверного URL;
- [ ] поведение при отсутствии FFmpeg;
- [ ] прерывание пользователем и очистку частичных файлов.

Для каждого сценария записать:

- команду или последовательность ответов меню;
- предусловия;
- ожидаемый результат;
- фактический результат;
- созданные файлы;
- код возврата;
- известные ограничения.

Использовать только легальные тестовые источники: собственные материалы,
public-domain fixtures или заранее подготовленные локальные образцы.

**Контрольная точка:** составлена таблица baseline; сломанные сценарии явно
отмечены и не выдаются за работающие.

### Step 3. Добавить защитные тесты

- [ ] Вынести минимальные seams для подмены `yt-dlp` и FFmpeg без изменения
  бизнес-поведения.
- [ ] Добавить smoke-тест точки входа CLI.
- [ ] Добавить characterization tests для формирования аргументов команд.
- [ ] Запретить реальную сеть в unit-тестах.
- [ ] Использовать небольшие локальные fixtures.
- [ ] Проверять имена и расположение выходных файлов.
- [ ] Проверять ошибки внешних процессов и отмену.

Phase 0 не требует высокого процента покрытия. Тесты должны защитить критические
сценарии перед Phase 1.

### Step 4. Очистить репозиторий

- [ ] Добавить `.gitignore` для виртуальных окружений, кешей, IDE, логов,
  временных файлов, загруженных медиа и результатов обработки.
- [ ] Удалить из tracking временные копии и generated-файлы.
- [ ] Удалить локальные FFmpeg/FFprobe-бинарники из tracking.
- [ ] Документировать установку FFmpeg как внешней runtime-зависимости.
- [ ] Заменить абсолютные пути переносимым разрешением конфигурации.
- [ ] Удалить дубликаты только после сравнения и подтверждения владельца.
- [ ] Проверить историю на секреты и крупные бинарники.
- [ ] При найденном секрете сначала ротировать его, затем отдельно согласовать
  очистку истории Git.

Не переписывать опубликованную историю автоматически: это разрушительное
действие и требует отдельного решения команды.

### Step 5. Сделать Python-проект воспроизводимым

Рекомендуемый минимум:

- [ ] выбрать одну поддерживаемую версию Python для CI и разработки;
- [ ] добавить `pyproject.toml`;
- [ ] объявить runtime и development dependencies;
- [ ] добавить console script entry point;
- [ ] зафиксировать стратегию lock-файла;
- [ ] настроить Ruff;
- [ ] включить mypy постепенно, не маскируя ошибки глобальным `ignore`;
- [ ] настроить pytest и test markers;
- [ ] добавить pre-commit;
- [ ] добавить `.env.example` только с безопасными заглушками;
- [ ] описать обнаружение `ffmpeg` и `ffprobe`.

Выбор package/lock tool нужно зафиксировать ADR после просмотра реального
репозитория. Не следует одновременно добавлять несколько конкурирующих
lock-файлов.

### Step 6. Добавить минимальный CI

GitHub Actions должен запускаться на pull request и push:

1. установка выбранной версии Python;
2. установка проекта из зафиксированных зависимостей;
3. `ruff check`;
4. проверка форматирования;
5. `mypy`;
6. `pytest`;
7. smoke-проверка CLI entry point.

Сетевые загрузки медиа в CI запрещены. Интеграционные тесты с установленным
FFmpeg должны быть отдельным job или marker.

### Step 7. Обновить документацию

- [ ] Переместить Project Vision в `docs/product/PROJECT_VISION.md` отдельным

- [ ] Создать корневой `README.md`.
- [ ] Описать установку Python и FFmpeg для поддерживаемых ОС.
- [ ] Описать запуск CLI и тестов.
- [ ] Указать правовые и пользовательские ограничения.
- [ ] Добавить `CONTRIBUTING.md`.
- [ ] Добавить шаблоны issue/PR.
- [ ] Завести milestone `Phase 0`.
- [ ] Связать задачи Phase 0 с этим чек-листом.

### Step 8. Подготовить handoff в Phase 1

- [ ] Составить карту текущих функций и будущих модулей.
- [ ] Отметить зависимости терминального UI от бизнес-логики.
- [ ] Определить места будущих adapters для `yt-dlp` и FFmpeg.
- [ ] Записать список глобального состояния и side effects.

## 7. Предлагаемое разбиение на pull requests

1. **Audit only** — отчёт, baseline и список рисков без изменения кода.
2. **Repository hygiene** — ignore-файлы, удаление generated assets и
   документация внешних бинарников.
3. **Python packaging** — `pyproject.toml`, entry point и lock-файл.
4. **Quality gates** — Ruff, mypy, pytest и pre-commit.
5. **CI and docs** — GitHub Actions, README и contribution workflow.

Маленькие PR упрощают проверку того, что cleanup не изменил поведение CLI.

## 8. Definition of Done

Phase 0 завершена только если:

- [ ] канонический legacy-код и исходный commit SHA известны;
- [ ] все отслеживаемые файлы классифицированы;
- [ ] подтверждённые CLI-сценарии записаны в baseline;
- [ ] CLI устанавливается из чистого checkout по README;
- [ ] зависимости воспроизводимы;
- [ ] FFmpeg и FFprobe не хранятся в Git;
- [ ] секреты, cookies и пользовательские медиа не отслеживаются;
- [ ] CLI имеет стабильную точку входа;
- [ ] критические сценарии защищены smoke/characterization tests;
- [ ] Ruff, mypy и pytest проходят локально и в CI;
- [ ] тесты не требуют обращения к реальным медиаплатформам;
- [ ] известные проблемы записаны как issues;
- [ ] подготовлена карта извлечения `downloader-core`;
- [ ] cleanup не содержит незаявленного функционального рефакторинга.

## 10. Риски и блокеры

| Риск | Реакция |
|---|---|
| Legacy-код отсутствует в новом репозитории | вести MeVAD как greenfield; импортировать старый код только отдельным решением |
| Нет зафиксированных зависимостей | восстановить версии из импортов и проверить в чистом окружении |
| CLI зависит от локальных путей | задокументировать baseline, затем добавить конфигурацию |
| Тесты требуют сеть | подменить границу внешнего инструмента |
| В Git есть большие бинарники | убрать из tracking; историю менять только по согласованию |
| Найдены секреты/cookies | ротировать, исключить и провести отдельную очистку истории |
| Cleanup ломает поведение | откатить конкретный PR и сузить изменение |
| Начинается преждевременный refactoring | вынести изменение в Phase 1 |

## 11. Первый следующий шаг

Инициализировать локальный Git, подключить канонический remote и создать
первоначальный коммит с Project Vision, Phase 0 и greenfield-аудитом. После
этого выбрать стратегию: начать чистую реализацию или отдельно импортировать
проверенные части прежнего CLI.
